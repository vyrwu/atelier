# atelier v1 — scope reset

**Status:** decision record. Input for the v1 development plan — not the plan itself.
**Date:** 2026-08-30
**Baseline:** this branch (`claude/atelier-major-redesign-f7mtib`, PR #100), unmerged, 10 commits ahead of `main` (v0.9.0 + #98).

---

## Purpose

atelier grew to ~20k lines of Go across seven weeks and nine minor versions, and
became two products in one binary: an intent-workspace manager for agent sessions,
and a tmux distribution with tool launchers and a plugin system. Only the first is
used. This document records the decision to reset atelier to its useful core and
ship that as a genuine **v1.0.0**, and captures the evidence and constraints a
development plan must respect.

The reset is a **hard reset in place**, not a new repository. atelier keeps its
name, history, CI, release tooling and issue tracker. The journey is preserved in
git history and `CHANGELOG.md`; the v1 working tree should read as though it was
designed on purpose.

## 2. Diagnosis

### 2.1 The unused features are not the problem

Deleting every feature that is genuinely unused (tool launchers, tool selector,
plugin registry, AWS assume-role) removes **2,745 src / 1,092 test — about 13%**.
The remaining 87% is the core. The over-engineering is in the core, not the
periphery.

### 2.2 ~20% of the codebase exists to manage the codebase

Not features; scaffolding to keep atelier consistent with itself:

- `state` (1,182 / 1,191) — topology, invariant codes, `reconcile --fix`
- `testtmux` (706) — isolated tmux servers for integration tests
- `seed` (839 / 647) — fixture scenarios to reproduce drift by hand
- `doctor` (350), `state_show` (215), `debuglog` (235), `perf` (138), `ai_usage` (152)

This is the tax on storing state in tmux. tmux is a mutable global with no
transactions and no schema, and options vanish when the server dies — so a kernel
with a validated entity graph, a self-healing reconcile loop, and a fixture harness
was built to compensate.

The `CLAUDE.md` architecture principle is the same signal read from inside: it
exists because the substrate leaks and every tool hits the same edge cases. A rule
enforcing discipline against a leaky substrate is a tax, not an architecture.

### 2.3 An abstraction chose the architecture

`internal/adapters/claude/claude.go:105`:

> `// No --settings/Stop-hook injection — recap + attention are pulled by the`
> `// refresh loop reading the transcript.`

A `Stop` hook is Claude Code-specific. An agent-generic port cannot assume hooks
exist, so the only agent-generic way to know an agent's status is to observe it
from outside — poll the transcript. The port did not merely cost 266 lines of
interface; **it made polling the only design consistent with its contract.**

Polling then required a 45-second daemon (`tools/workspaces/refresh_loop.go`,
`defaultRefreshInterval = 45 * time.Second`), transcript discovery and tailing
(~500 lines of `adapters/claude`), worktree delta computation (`delta.go`), health
tracking and mtime-keyed throttling — and `internal/state` to repair what the loop
leaves behind when it dies.

Downstream cost of the abstraction: **~2,900 lines.**

Supporting evidence:
- `internal/integration` (the port) is imported by **9 packages** — the generic
  contract is the vocabulary of the whole codebase, not a contained seam.
- `internal/adapters/mock` (258 / 190) is imported only by tests, `seed`, and the
  registration in `cmd/atelier/integrations.go`. It is not a feature. It is 448
  lines existing to prove a port works that has one real implementation.

### 2.4 The UI cannot be smooth in its current shape

`internal/initgen/bindings.go` binds every view to `display-popup -E '<a new
atelier process>'`. A view transition is therefore: tear down a popup client →
spawn a new popup client → fork a new process → draw from zero. Two processes that
never co-exist cannot be animated between. `bindings.go:429` documents the
workaround this forces (a popup spawning a sibling popup must fire `display-popup`
inline in the tmux binding or it targets the wrong client).

`popup.ApplyStyle` reconfiguring key-table, status line and prefix on every open
makes the flash structural.

This is **not** tmux's rendering. k9s, lazygit and btop all feel smooth inside
tmux; what they share is one long-lived process owning one pane, with views as
internal state. `DECISIONS.md:25` records the choice that produced the current
shape:

> **M-c in fzf; bubbletea reintroduced for the M-n input only.** The pickers
> (M-s, M-c) stay fzf... fzf remains the picker technology.

There is no stalled bubbletea migration. bubbletea v1.3.10 is in `go.mod` and fully
used in `textprompt`, `notify` and `spinner`. The wholesale migration was
deliberately declined. Reaching a solid TUI means **reversing that decision**, not
finishing a migration.

### 2.5 What #100 got right

The intent-workspace record matches the real workflow better than it was credited:

```go
type Workspace struct {
    Worktrees []Worktree   // slice — mutable after creation
    PRs       []PR         // slice
}
func AddWorktree(h, session, root, repoPath, repo, branch, wtPath string) (statestore.Worktree, error)
```

Both are slices, `AddWorktree` adds a repo *after* creation, and the interactive
agent receives the atelier MCP server (`cfg.MCP` → `--mcp-config`) while background
naming/recap calls do not. So an agent can add a worktree and register a PR
mid-task. That is exactly "one workspace, sequential PRs" and "go reach into
another repo." **This is the designed path and it survives v1 intact.**

## 3. Real usage (the scope v1 serves)

Stated by the maintainer, and the only workload v1 targets:

- Create a workspace for a task, **manually specifying the repos**.
- The workspace produces **multiple sequential PRs**, or the agent is explicitly
  asked to reach into other repos and open PRs there.
- **GitHub only.** No other forge.
- **Claude Code only.** No other agent.
- Core need: *"switching between sessions that are running Claude, and knowing
  which to open when."*
- Quality bar: **seamless, smooth transitions between views.** This is the thing
  that makes the tool worth existing over a bare tmux setup.

Explicit non-goals: multi-forge, multi-agent, tool launching, plugins, being a
tmux distribution.

## 4. Decisions

### 4.1 Architecture

| # | Decision | Rationale |
|---|---|---|
| D1 | **Headless core, three thin consumers.** A data/aggregation core with no terminal awareness; TUI, CLI (for hooks) and MCP (for the agent) all sit on top of it. | Testable, fast, keeps terminal concerns from leaking into the data layer — the failure that produced §2.2. |
| D2 | **One long-lived bubbletea process, popup-attached.** Views are internal model state, never separate processes. No fzf. See §4.3 for the surface split. | The jank is process-per-open, not popups. A popup attached to a warm process reappears instantly, already populated; every transition inside it is in-process. See §2.4, §4.3. |
| D3 | **Hooks, push not pull.** `Stop` → write status + spawn a detached recap job. `Notification` → blocked. No ticker, no daemon liveness, no reconcile. | Deletes ~1,900 lines and an entire failure class. A hook has no liveness requirement. |
| D4 | **Concrete modules, not ports.** No interface with a single implementer; no mock built to justify an abstraction. | See §2.3. `internal/tmuxhost` (356 src, one concrete client, every tmux call funnelled through it) is the pattern to copy — swap-ability without the interface. |
| D5 | **statestore is the sole source of truth.** tmux never stores state. No `@`-prefixed window options as data. | Removes the root cause of §2.2. |
| D6 | **tmux demoted to a dumb PTY host.** `new-session`, `switch-client`, `kill-session`. Nothing else. | The seam is already 356 lines; keep it that size. Writing a custom multiplexer was considered and rejected — the one transition tmux cannot smooth (into a live agent pane) is exactly the one that would require a VT emulator. |
| D7 | **Go.** | bubbletea, `os/exec`, `encoding/json` are all already proven here, and ~480 lines of working bubbletea UI (`textprompt`, `notify`, `spinner`) port directly. The project's risk is scope discipline; a language learning curve loads risk onto that exact axis. Rust/Zig belong in a project where the language is the point. |

### 4.2 Repo and release

| # | Decision |
|---|---|
| D8 | **Hard reset in place. No new repository.** Delete at once, re-add only what is consciously chosen. Keeps name, history, CI, release tooling, issues — and makes v1.0.0 mean something. |
| D9 | **Merge #100 to `main` before the reset.** The keep-list packages exist only on this branch; merging puts them in `main`'s history so the reset builds on them rather than resurrecting them from a closed PR. Optionally cut **0.10.0** on the merge so the full intent-workspace redesign has a checkout-able tag. |
| D10 | **The reset is one commit,** clearly titled, on a `v1` branch. The discontinuity should be visible in `git log`, not smeared across thirty deletions. |
| D11 | **Ship as 1.0.0** via an explicit `Release-As: 1.0.0` footer. See §8. |

### 4.3 Presentation surfaces

v1 has **one process** but **three surfaces**. Conflating them was the original
design error; collapsing them now would be the mirror of it.

| surface | hosts | lifetime | why |
|---|---|---|---|
| **tmux status line** | attention rollup, workspace description | always visible | When you need to know *which* session wants you, you are looking at a Claude pane — not at a picker. The signal must be ambient. Already implemented: `status-left` shells `atelier status description` and `atelier status attention count`. This is **not** part of the TUI and must not become part of it. |
| **popup** | the TUI: sessions list, new-workspace input, confirms | transient — seconds | M-s is *peek and jump*. An overlay is one transition; a dedicated TUI window would be two (switch to it, then switch to the target). |
| **window** | Claude Code sessions, shells | durable — hours | Survives detach/reattach, keeps full scrollback and copy mode, and appears in tmux's own window list — which the status line reads. |

**Popup ≠ process-per-open.** `internal/popup/popup.go` already backs popups onto
persistent detached sessions (`Ensure` … `EnsureAndAttach`), so the process outlives
the popup closing. tmux repaints the pane from its own buffer on re-attach, so a
warm process reappears *instantly*, already rendered. The jank in §2.4 came from
popups that **fork a fresh process and draw from zero** — not from popups.

**Claude sessions stay windows** (`internal/workspace/workspace.go:206`,
`new-window`). Moving them into popups would: lose the view on detach (the process
survives in its backing session, but tmux keeps no record of which popups were
open — you would rebuild that in the statestore, which is re-implementing window
management); remove them from the tmux window list the status line depends on; and
make every interaction popup-from-popup, the fragile path documented at
`bindings.go:429`.

**Corollary — the popup key-table nearly disappears.** `bindings.go` today carries
**10 `bind -T popup` against 4 `bind -T root`**: popups host fzf and shells that do
not handle their own keys, so bindings are defined twice. A bubbletea TUI consumes
its own keystrokes, so v1 needs essentially one popup binding — the one that opens
it. This holds *only* while popups host the TUI and nothing else.

**Style once, not per attach.** `popup.ApplyStyle` currently rewrites key-table,
status line and prefix on every attach; that churn is the visible flash. Apply the
style to the backing session once, at creation.

**`internal/workspace` (1,636 / 2,083) — resolved, still needs the read-through.**
The layout is simplified (§11 Q1): **a workspace is a directory, and its worktrees
live inside it.**

```
~/ateliers/<slug>/
  <repo>/<branch>/     ← the git worktree itself, not a symlink
```

The symlink indirection goes with the repo-local `~/code/.worktrees/...` tree —
`git worktree add` can place a worktree anywhere, so the indirection bought
nothing v1 needs. What survives from this package is directory creation, worktree
add/remove, and slug derivation. The tmux option plumbing in the same package
goes. It still needs reading line by line to split, but the target shape is no
longer in question.

**Consequence to get right:** with worktrees living inside the workspace
directory, deleting a workspace must run `git worktree remove` (or
`git worktree prune`) against each source repo. Deleting the directory alone
leaves stale worktree metadata in every repo the workspace touched. This is the
one piece of real bookkeeping v1 owes.

## 7. Build fresh

1. **The TUI** — one warm bubbletea process, popup-attached (§4.3). It is the
   product; build it first, not last. Four views: sessions list, new-workspace
   input, confirm dialogs, and the minimal per-workspace PR list (§11 Q3).
   Replaces ~1,050 lines of fzf pickers.
2. **The hook CLI** — `Stop` and `Notification` handlers writing through the core.
3. **The MCP wrapper** — small. Two or three tools (add worktree, register PR),
   not a surface.
4. **A static tmux fragment, not a generator.** `initgen` is 617 lines because
   atelier has ~15 bindings across two key-tables plus hooks. v1 needs roughly
   this, and it is the whole of it:

   ```tmux
   # the TUI — one warm process, popup-attached
   bind -n M-s run-shell 'atelier ui --view sessions'
   bind -n M-n run-shell 'atelier ui --view new'

   # per-workspace scratch shell — pure tmux, no atelier code
   bind -n M-t display-popup -w 80% -h 80% \
     -E "tmux new-session -A -s scratch-#{session_name}"

   # shell in the current directory — pure tmux
   bind c new-window -c "#{pane_current_path}"
   ```

   Ship it as a checked-in file the user sources with one README line. **If a
   generator ever becomes necessary again, that is the signal there are too many
   bindings.**

### Where a capability lives

The test that decides every case, and retires `toolselector`:

> **Does it need to know about workspaces?**
> - **No** → tmux config. Scratch shell, shell in cwd, splits, copy mode, resize.
> - **Yes** → an action inside the TUI, where the workspace list already lives.
> - **Never** → a separate `atelier` subcommand launched from a keybinding.

That third line is the pattern that produced §2.4: a binding forking a process that
re-queries everything and draws from zero.

Worked example — the two shell tools:

- **Popup Shell** does not need to know about workspaces (`#{session_name}` scopes
  it), so it is config. One line, above.
- **Shell in a worktree** does — `worktree_open.go` exists to *pick* one of the
  workspace's worktrees. In v1 you are already looking at that list in the TUI:
  highlight a worktree, press a key, the TUI issues `new-window -c <path>` through
  `tmuxhost`. Five lines inside the program, no picker, no process.

**Loose end:** atelier reaps orphaned popup backing sessions via `window-unlinked`
/ `session-closed` hooks calling `atelier popup cleanup`. Pure config cannot do
that, so `scratch-*` sessions accumulate as workspaces die. Cheapest fix: the TUI
prunes orphans at startup — it already enumerates sessions, so this is a loop, not
a subsystem. Do not rebuild the hook machinery for it.

## 9. Mechanical gotchas

**Release-please will not give you 1.0.0 by default.** `release-please-config.json`
sets:

```json
"bump-minor-pre-major": true
```

On 0.x a breaking change bumps the **minor** — a `feat!:` reset commit yields
**0.10.0**, not 1.0.0. Use an explicit footer on the reset commit:

```
Release-As: 1.0.0
```

(Or flip `bump-minor-pre-major` to `false` and let `feat!:` carry 0.9.0 → 1.0.0.
The footer states intent more clearly.)

**`RELEASING.md` documents a smoke test that will not compile after the reset:**

```bash
atelier doctor               # tmux + every plugin OK
atelier status freshness '0' '0' '' '1729094400' '/fake/repo'
```

Both commands are dropped and "every plugin OK" describes a subsystem that no
longer exists. Update the runbook in the same PR.

**`CLAUDE.md` — replace, do not edit.**

| section | disposition |
|---|---|
| Architecture principle ("tools never re-implement window management") | **delete.** It exists to police the tmux-as-database leak being removed. Keeping it re-imports the problem it was written for. |
| Testing rule | **keep verbatim.** It is why the keep-list packages carry 1,840 lines of tests worth porting. |
| Commit + PR rules | **keep.** Conventional Commits drive release-please. |
| GitHub issue conventions | **drop the area-label taxonomy** (`ux`/`usability`/`config`). Overhead for a 5k-line tool. |
| "When the principle doesn't hold" | **delete** with the principle. |

Replace what is removed with the scope statement (§3) and the budget rule (§10).

**Docs to delete in the reset:** `DESIGN.md`, `DECISIONS.md`, `REFACTOR.md`. They
argue for the model being replaced. Git history and `CHANGELOG.md` preserve them.
A short `docs/history.md` written afterwards is worth more than three documents
defending a superseded design.

## 10. Constraints for v1

Written as tripwires, not sentiments. atelier did not fail from bad decisions; it
failed from good local decisions with no budget.

- **One agent. One forge. One renderer.** A second implementation requires deleting
  the first.
- **No plugin system. Ever.** It is the seed of most of §5.
- **State lives in one file, never in tmux.**
- **No process spawn per view.** Popups are fine; popups that fork a fresh process
  and draw from zero are not. If it draws, it draws inside the one warm program.
- **Extract an interface only when a second real implementation exists and is in
  production.** Never for a mock. Never for a hypothetical.
- **Hard budget: 5,000 lines of `internal/`.** Adding past it means removing first.
- **A feature ships only after it has been wanted three separate times.** Not once,
  with a good rationale.

Target: **4,000–6,000 src lines** — roughly a quarter of the current tree — doing
the 90% that is actually used, with `repoindex` finally receiving the majority of
the attention.

## 11. Resolved

All seven questions from the first draft are answered. Recorded with their
consequences.

| # | question | resolution |
|---|---|---|
| Q1 | `internal/workspace` triage | **A workspace is a directory; worktrees live inside it.** No symlink tree, no repo-local `~/code/.worktrees`. See §6 for the shape and the `git worktree remove` obligation. |
| Q2 | Does the recap survive? | **No.** Dies outright. 7–10 concurrent workspaces today, but the intent model collapses many of those into one workspace with N worktrees, and the recap was the weight that justified the entire polling architecture. The `Stop` hook sets status only. |
| Q3 | Does M-c survive? | **Yes, minimal.** Per-workspace PR list: state, CI, approved-or-not, and one shortcut to open the PR. Nothing else. Not a separate popup tool — a view inside the TUI. |
| Q4 | MCP surface | **Keep.** `add_worktree` and `register_pr`. |
| Q5 | Binary shape | **One binary**, `atelier ui` subcommand. Hook latency is a non-issue at single-digit-ms Go startup firing once per agent stop. |
| Q6 | `atelier doctor` | **Delete.** It diagnosed a plugin registry, a daemon, and state scattered across tmux options. None of those exist in v1. |
| Q7 | Test strategy | **Err toward removal.** v1 is a new program; its tests are new. See §11.2. |

### Q3 in detail — the minimal PR view

No new data work is required. `statestore.PR` already carries every field:

```go
State          string  // open|draft|merged|closed
CI             string  // pass|fail|pending|none
ReviewDecision string  // approved|changes_requested|review_required|none
URL            string
```

and `adapters/github` already requests `reviewDecision` and `url` in its single
batched `gh pr list --json` call. So the view is a render over `Active().PRs` plus
one action (open `URL`). What gets dropped is `forge.go`'s 300-line fzf surface,
not the data behind it.

Explicitly deferred, and requiring the three-times rule to return: PR creation,
merge, checkout, comment, review, CI log tailing.

## 11.1 Still open — one follow-on from Q2

**Does workspace auto-naming survive?**

Killing the recap removes most model calls, but not all. `naming.go` (167) drives
`GenerateName` through `claudegen` to derive a workspace title from the typed
intent. If it survives, so do `claudegen`, its token accounting, and a background
subprocess path — the last of the machinery Q2 was meant to remove.

**Recommendation: kill it too.** The intent is typed by hand; a slug of its first
few words, or a short title typed alongside it, costs nothing and reads no worse.
A model call to name a thing you just finished describing is ceremony. Killing it
means **v1 makes zero model calls**, `claudegen` goes entirely, and there is no
background process of any kind left in the tool.

This is a UX preference, not an architectural one — hence recorded rather than
decided.

## 11.2 Test strategy

The instruction is to remove aggressively: v1 is effectively a new program and its
tests will be written new. Applied with one carve-out that costs nothing:

- **Port tests only for packages copied verbatim** — `statestore` (1,019),
  `repoindex` (173), `github` (245), `config` (127). They already pass, they test
  code that is not changing, and they are the safety net while everything around
  them is gutted. Porting them is free; re-deriving them later is not.
- **Drop everything else**, including all 2,083 lines under `internal/workspace` —
  that package is being reshaped, so its tests describe the old shape.
- **Do not port `testtmux` (706).** It was sized for 14 packages issuing tmux
  verbs. With one 356-line seam, a fake `tmux` on `PATH` or a small hand-rolled
  double is likely sufficient. Decide deliberately rather than porting out of habit.
- **Do not chase the old coverage numbers.** The `CLAUDE.md` testing rule (kept,
  §9) governs new code from here: every fix and feature lands with tests.
