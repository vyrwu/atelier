# atelier v1 — Design Document

**Status:** the design, now implemented. Kept as the reference for why the system
is shaped the way it is.
**Audience:** anyone changing atelier.
**Scope:** the built system on its own terms. Not a migration plan. Where the
implementation resolved a question this document once left open, the resolution
is recorded here.

---

## 1. What atelier is

atelier is a **switchboard for parallel Claude Code sessions.**

You describe a task in plain language. atelier gives it a workspace — a
directory, a name, and an agent — and gets out of the way. The agent does the
work: finds the repositories, creates the worktrees, writes the code, opens the
pull requests. atelier's job is to let you run several of these at once and
always know which one wants you.

Three things, and nothing else:

1. **Start work** — one prompt, one keystroke, an agent running in a directory,
   started in the background so kicking off work never breaks your focus.
2. **Know where to look** — an ambient signal telling you which session is
   blocked, without leaving what you are doing.
3. **Get there fast** — switch between sessions, worktrees, and pull requests
   with no perceptible delay; retire finished work and restore it later.

### Explicit non-goals

atelier is **not**:

- a tmux distribution, configuration framework, or theme
- a tool launcher, plugin host, or registry
- a multi-agent orchestrator
- a git porcelain, code review tool, or CI dashboard
- a general-purpose terminal multiplexer

It supports **one agent** (Claude Code) and **one forge** (GitHub). This is a
design decision, not a limitation to be worked around. Any abstraction that
exists to support a second implementation is out of scope until a second
implementation actually exists.

## 2. Domain model

Four entities. Everything in the system is one of these.

| Entity | Definition | Identity | Lifetime |
|---|---|---|---|
| **Workspace** | One task. A directory, a title, a tmux session, and an agent. Either **active** or **retired**. | Immutable slug (directory name) | Until deleted |
| **Worktree** | A git worktree belonging to a workspace, living inside its directory. | `<repo>/<branch>` path under the workspace root | Until removed |
| **Agent session** | A Claude Code process in the workspace session's `claude` window. | tmux session + window name | Until the process exits |
| **Pull request** | A GitHub PR whose head branch matches one of the workspace's worktrees. | `owner/repo#number` | Owned by GitHub |

**Cardinality:** one workspace has one agent session, N worktrees, and N pull
requests. A worktree belongs to exactly one workspace. A pull request is
associated with a workspace by branch, not by ownership.

**Lifecycle.** A workspace is created **active** and stays in the working set.
**Retiring** it (`Retired` on the record; zero value = active, so old state loads
active with no migration) kills its processes but keeps its directory, worktrees,
and Claude conversation on disk. **Restoring** a retired workspace resumes the
agent. **Deleting** is separate and permanent (§ Epic F). Retire/restore is the
one deliberate exception to "no recovery of removed workspaces" — a soft state,
not an undo of a destructive one.

**Windows are named, not indexed.** A workspace session's windows are `claude`
(the agent), `shell` (a workspace-dir shell), and one per worktree
(`<repo>-<branch>`, sanitised). All in-workspace navigation is keyed on these
names, so the dedicated tmux server runs with `automatic-rename off` and
`allow-rename off` — a silent rename would drift the identity nav depends on.

### Filesystem layout

```
~/ateliers/<slug>/                    workspace root — the agent's cwd
  <owner-repo>/<branch>/              a git worktree, created by the agent
    .git                              file (not directory) — marks a worktree
```

The workspace directory **is** the record of its worktrees. Nothing else needs
to track them.

**The slug is immutable.** It is derived at creation and never changes, because
git worktree metadata stores absolute paths — renaming the directory after a
worktree exists would break every repository the workspace touched. The
human-readable **title** is separate, lives in state, and may change freely.

## 3. Functional requirements

Written as user stories with acceptance criteria. Each is independently
testable and independently deliverable.

### Epic A — Starting work

**FR-A1 — Create a workspace from an intent, in the background**
> As a user, I can press a key, type what I want to do, and press Enter, so that
> work starts without me filling in a form — and without pulling me out of what
> I am already doing.

- Given the new-workspace view is open
- When I type free text and press Enter
- Then the popup closes immediately and the workspace is built in the
  background (a detached builder names it, lays out the directory, and launches
  the agent); a status-line toast confirms when it is ready
- And I stay exactly where I was — pressing ⌥Enter instead both builds it and
  switches me in once it is ready
- And I am never asked to select repositories, branches, or a template

**FR-A2 — The workspace names itself, and its directory**
> As a user, my workspace and its directory get a short readable name derived
> from my intent, so that I can recognise it in a list.

- Given a workspace is being created from intent text
- Then Claude names it, and both the title and the immutable directory slug
  derive from that name — not from the raw prompt
- And a workspace always has a usable name, falling back to a deterministic
  title from the intent if naming is disabled or fails
- And because creation runs in the background, the naming call never makes you
  wait (NFR-P2)

**FR-A3 — Creation is a directory, nothing more**
> As a user, my workspace is a real directory I can `cd` into, so that
> everything about it is inspectable with ordinary tools.

- Given a workspace exists
- Then `~/ateliers/<slug>/` exists on disk
- And the agent's working directory is that path
- And no repositories are cloned, indexed, or fetched by atelier at creation

**FR-A4 — The agent finds its own repositories**
> As a user, I can name repositories in my intent text and have the agent
> locate or clone them, so that atelier does not need to maintain an index of
> my code.

- Given an agent session in a workspace
- Then the agent knows the workspace root path
- And the agent is responsible for discovering, cloning, and creating worktrees
- And atelier performs no repository indexing of its own

### Epic B — Knowing where to look

**FR-B1 — Ambient attention signal**
> As a user, I can see how many sessions need my attention while I am working
> inside any pane, so that I do not have to open a picker to find out.

- Given one or more agent sessions are **blocked** waiting on my input
- When I am attached to any pane in any session
- Then a count of blocked sessions is shown in the status line, highlighted
- And it updates within one second of an agent becoming blocked or unblocked
- And **only blocked counts.** A working agent does not badge; an idle agent
  does not badge. When no session is blocked, the badge is inactive — it does
  not draw the eye
- And the badge therefore means "something needs you", never "something
  happened"

**FR-B2 — Current workspace is always identified**
> As a user, I can see which workspace I am currently in from the status line,
> so that I never lose my place.

- Given I am attached to a workspace session
- Then that workspace's title is shown in the status line

**FR-B3 — Per-session status in the list**
> As a user, I can see at a glance which sessions are working, which are waiting
> on me, and which are idle.

- Given the sessions view is open
- Then each workspace shows exactly one of: **working** (agent is executing),
  **blocked** (agent is waiting on my input), **idle** (agent has finished and
  is not waiting), **gone** (no live agent process)
- And the state shown reflects reality within one second of it changing
- And only **blocked** is rendered as an attention state; **working**, **idle**
  and **gone** are informational and visually quiet (consistent with FR-B1)

### Epic C — Switching

**FR-C1 — Switch to any active session**
> As a user, I can open the active-workspaces list (`M-a`) and jump into any one
> of them in two keystrokes, landing on the agent.

- Given the active-workspaces view is open
- When I select a workspace and press Enter
- Then the view closes and I am attached to that workspace's `claude` window
- And if the session had died (tmux-server or machine restart), it is revived
  and the conversation resumed (`claude --continue`) first — select the agent
  window, then switch the outer client to it, in that order

**FR-C2 — Filter by typing**
> As a user, I can narrow the session list by typing, so that I can reach a
> workspace by name without scrolling.

- Given the sessions view is open with more entries than fit on screen
- When I type characters
- Then the list filters to matching titles, in real time

**FR-C3 — Return to where I was**
> As a user, closing the picker without selecting puts me back exactly where I
> was, so that looking costs me nothing.

- Given I opened the picker from inside a session
- When I dismiss it without selecting
- Then I am returned to the same pane, with its content intact

### Epic D — Worktrees and shells

**FR-D1 — Worktrees have their own view**
> As a user, I can open a list of every worktree across my workspaces, so that I
> can jump to any of them.

- Given worktrees exist on disk under one or more workspaces
- When I open the worktrees view (`M-t`)
- Then every worktree is listed, grouped by workspace, showing repository and
  branch
- And worktrees created by the agent appear without any registration step — the
  list is derived from disk

*Note: v1 first nested worktrees beneath their workspace in the switcher. It
proved noisy, so worktrees became their own view and the workspace lists stay
flat — an active row surfaces its open-PR count instead.*

**FR-D2 — Each worktree has a dedicated, persistent shell**
> As a user, I can drop into a shell in any worktree and swap between worktree
> shells without losing what is running in them.

- Given the worktrees view is open with a worktree selected
- When I press Enter
- Then a shell window dedicated to that worktree opens in its workspace session,
  at the worktree path, and I am switched to it
- And that window is reused on return (keyed by `<repo>-<branch>`), so a
  background job started there keeps running and `M-t` swaps between them
  seamlessly

**FR-D3 — Agent and shell are one keystroke apart**
> As a user, inside a workspace I can toggle between Claude and a shell, and
> never lose Claude.

- Given I am in a workspace session
- When I press `M-c` I land on the `claude` window; when I press `M-s` I land on
  a workspace-directory shell (created if absent)
- And if I had exited Claude, `M-c` respawns and resumes it — it always brings
  the agent back
- And `M-q` detaches atelier entirely, returning me to the shell that launched it

### Epic E — Pull requests

**FR-E1 — See the workspace's pull requests**
> As a user, I can see the pull requests for my current workspace with their
> state, CI result, and whether they are approved.

- Given a workspace whose worktree branches have open pull requests
- When I open the pull request view
- Then each PR is listed with: repository, number, title, state
  (open/draft/merged/closed), CI result (pass/fail/pending/none), and review
  decision (approved/changes requested/review required)

**FR-E2 — Open a pull request**
> As a user, I can open any listed pull request in my browser with one key.

- Given the pull request view is open
- When I select a PR and press the open key
- Then that PR opens in my default browser

**FR-E3 — Pull requests appear without being registered**
> As a user, pull requests the agent opens show up on their own, so that I never
> discover an empty list because the agent did something in an unexpected way.

- Given the agent has pushed a branch and opened a PR from a worktree in the
  workspace
- When I next open the pull request view (`M-r`)
- Then that PR is listed, with no registration step having occurred
- And the agent opens PRs as **drafts** via the `create_pr` MCP tool — rebased
  onto the freshly-fetched default branch, pushed with the `gh` token over HTTPS
  so it never prompts for a key — and may `register_pr` any it opens that branch
  matching would miss (FR-G2)

**FR-E4 — Freshness follows the agent**
> As a user, pull request state is current when I look at it, without anything
> running in the background.

- Given an agent session finishes a unit of work
- Then the workspace's pull request state is refreshed
- And no periodic timer, daemon, or background poller exists

### Epic F — Ending work

**FR-F0 — Retire and restore, without deleting**
> As a user, I can clear finished work out of my active list without losing it,
> and bring it back later.

- Given an active workspace
- When I retire it (`M-d` in the active list)
- Then its processes are killed but its directory, worktrees, and Claude
  conversation are kept, and it leaves the active list — no confirmation, it is
  lossless and reversible
- And it still appears in the all-workspaces list (`M-w`); selecting it there
  restores it, resuming the agent where it left off

**FR-F1 — Delete a workspace cleanly**
> As a user, I can delete a workspace and have it leave no trace in any
> repository it touched.

- Given a workspace with worktrees in one or more repositories
- When I delete it and confirm
- Then each worktree is removed via git so no stale worktree metadata remains
  in any source repository
- And the workspace directory, tmux session, and state entry are removed
- And if any worktree has uncommitted changes, I am warned before anything is
  removed

**FR-F2 — Deletion is confirmed**
> As a user, destructive actions ask me first.

- Given I trigger a delete
- Then I must confirm before anything is removed
- And the confirmation names what will be destroyed

### Epic G — Agent integration

**FR-G1 — The agent knows its workspace, and is set up to work in it**
> As a user, the agent I am talking to knows which workspace it is in, where to
> put things, and has the tools to do so without prompting me.

- Given an agent session starts
- Then the workspace root path and identity are available to it in its
  environment, and its working directory is the workspace root
- And atelier has prepared the directory for Claude: it is pre-trusted (no
  folder-trust prompt), atelier's MCP server is registered for it, and its
  `CLAUDE.md` is a symlink to a central per-workspace guide
- And those writes go to Claude's real config, honoring `$CLAUDE_CONFIG_DIR`
  rather than assuming `~/.claude`

**FR-G2 — The agent's tools: create, and register what cannot be discovered**
> As a user, the agent can create worktrees and pull requests correctly, and a
> PR it opened without a local worktree still shows up in my list.

- Given an agent session in a workspace
- Then it has `create_worktree` (a worktree off the freshly-fetched default
  branch, placed where atelier can see it), `create_pr` (rebase + draft PR), and
  `register_pr` through atelier's MCP interface
- And a PR it registers appears in the pull request view and persists across
  refreshes — `register_pr` is the gap-filler for anything branch matching misses

**FR-G3 — Non-compliance degrades, never breaks**
> As a user, an agent that does something reasonable but unexpected costs me
> visibility of one item, never a broken workspace.

- Given the agent performs a git or GitHub operation without using atelier's
  interfaces
- Then atelier's own state remains valid
- And anything derivable from the filesystem or GitHub still appears

## 4. Non-functional requirements

### Performance

**NFR-P1 — Nothing on the hot path touches the network.**
Opening any view renders from local state. Network calls (GitHub) happen
asynchronously and update the view when they land.

**NFR-P2 — Workspace creation never makes you wait.**
Pressing Enter closes the popup immediately and hands the work to a detached
builder; nothing blocks your focus. The builder names the workspace (so the
directory is named from the title, not the raw prompt) and launches the agent
off the hot path; a status-line toast confirms when it is ready.

**NFR-P3 — Views render instantly from local state.**
Opening a view renders from the local state file with nothing on the hot path
touching the network (NFR-P1). The overlay runs fresh in the popup each time —
deliberately small and local, so it draws immediately — rather than a warm
attached process. (The one long-lived UI process is the home splash.)

**NFR-P4 — In-overlay transitions are internal state.**
Moving between the overlay's screens (active, all, new, pull requests, worktrees,
confirm) is internal state change in one process — no new spawn, no clear-screen,
no visible reconstruction.

**NFR-P5 — Zero cost when idle.**
With no user interaction and no agent activity, atelier consumes no CPU. There
is no timer, no tick, and no polling loop anywhere in the system.

### Reliability

**NFR-R1 — No daemon.**
No component's correctness depends on a background process staying alive. State
changes are pushed by events, not discovered by sweeps.

**NFR-R2 — Ground truth over bookkeeping.**
Where reality can be read cheaply, it is read rather than tracked. Worktrees are
derived from the filesystem; pull requests from GitHub. Stored state is a cache
and an index, never the only record of something that exists elsewhere.

**NFR-R3 — State survives everything.**
Workspaces, titles, and cached PR data survive tmux server restart, machine
restart, and process crash. Nothing atelier needs is stored in tmux.

**NFR-R4 — Concurrent writes are safe.**
The UI and hook-invoked CLI both write state. Writes are atomic and serialised;
a crash mid-write leaves the previous valid state intact.

**NFR-R5 — Stale status is detected.**
If an agent process dies without reporting, its session is shown as **gone**
rather than retaining its last known status.

**NFR-R6 — Agent cooperation is never load-bearing.**
No requirement in §3 depends on the agent choosing to call an atelier
interface, except FR-G2, which is explicitly a gap-filler.

**NFR-R7 — tmux is a fallible dependency, handled as one.**
All tmux use goes through one seam with a short exec timeout, so a wedged server
surfaces as an error rather than a hang (attach is the one legitimate block, and
goes through `syscall.Exec`, not the seam). Navigation is keyed on window names,
not indices, with automatic renaming disabled; window and worktree names are
sanitised because tmux treats `/` and `:` as target syntax; switching lands with
`select-window` then `switch-client -c <outer>`. atelier deliberately does **not**
carry a reconcile/repair kernel: the overlay runs the program directly in the
popup and captures-and-uses the invoking client immediately, so the stale-outer
and orphan-popup failure classes that kernel existed to fix do not arise.

### Simplicity

**NFR-S1 — Line budget: 5,000 lines of `internal/`.** Adding beyond it requires
removing first.

**NFR-S2 — One binary.** A single `atelier` executable serves the UI, the CLI,
and the MCP server.

**NFR-S3 — One state file, one config file.** Both plain text, both hand-editable,
both inspectable without tooling.

**NFR-S4 — Terminal configuration is a static file the user sources.** atelier
never generates, rewrites, or owns the user's tmux configuration.

**NFR-S5 — One renderer.** All user interface is Bubble Tea. No second UI
technology, no external picker binary, no shelling out to draw.

### Operability

**NFR-O1 — Failures explain themselves in one line.** When atelier cannot start
or cannot complete an action, it states the reason and what to do, then exits.
There is no diagnostic subsystem.

**NFR-O2 — Platforms:** macOS and Linux. Requires tmux, git, and the GitHub CLI
on `PATH`.

## 5. Architecture

### 5.1 One process, three surfaces

The user sees things in four places. Conflating them is the primary
architectural risk.

| Surface | Hosts | Lifetime | Rationale |
|---|---|---|---|
| **Status line** | Attention count, current workspace title | Visible in workspaces (hidden on the splash) | When you need to know which session wants you, you are looking at an agent pane — not at a picker. The signal must be ambient (FR-B1, FR-B2). |
| **Home splash** | The landing screen and its legend | Persistent | Attaching lands you on a real screen, not a bare shell. This is the one long-lived UI process. |
| **Overlay (popup)** | active / all / new / pull requests / worktrees / confirm | Seconds | Peek and jump. An overlay is one transition; a dedicated window would be two. It runs **fresh** each open (NFR-P3) — small and local, it draws instantly, and captures the invoking client at open time so it never operates on a stale one. |
| **Window** | Agent (`claude`), shells (`shell`, per-worktree) | Hours | Survives detach and reattach, keeps full scrollback and copy mode, and is visible to the terminal multiplexer's own session list. |

**Agent sessions are windows, never overlays.** An overlay is bound to a client
and does not survive detaching; a session you live in for hours must.

Keyboard input is owned by whichever surface is focused. The terminal
multiplexer's own bindings do two jobs: open an overlay on a chosen screen
(`M-a`/`M-w`/`M-n`/`M-r`/`M-t`), and move between windows inside a workspace
without an overlay at all (`M-c` Claude, `M-s` shell, `M-q` detach).

### 5.2 Capture design

The central problem: the agent creates worktrees and pull requests
autonomously. atelier must reflect them without being able to control what the
agent does.

Five mechanisms exist. They are not equally reliable:

| Mechanism | Reliability | Depends on |
|---|---|---|
| **Derive** — read ground truth on demand | Cannot fail; nothing is being captured | The data being derivable |
| **Constrain** — make the wrong path unnatural | N/A — makes derivation valid | Nothing |
| **Intercept** — an event hook fires | Deterministic where the event exists | Hook installation |
| **Register** — the agent calls an interface | Only as reliable as agent compliance | The agent choosing to |
| **Instruct** — the prompt asks | Probabilistic | The agent choosing to |

**Governing principle: agent compliance is never load-bearing** (NFR-R6).
Register and Instruct are conveniences layered on mechanisms that work without
them.

Applied:

| Subject | Primary | Made valid by | Gap-filler |
|---|---|---|---|
| **Worktrees** | **Derive** — walk the workspace directory; a `.git` *file* marks a worktree | **Constrain** — the agent's cwd is the workspace root, so `git worktree add ./repo/branch` is the natural form | — |
| **Pull requests** | **Derive** — one batched `gh pr list --json` per repository, matched on head branch | **Intercept** — the agent's stop event triggers the refresh (FR-E4) | **Register** — MCP, for PRs with no local worktree (FR-G2) |
| **Agent status** | **Intercept** — session-start, stop, and notification events | Environment variables identify the workspace and window | **Derive** — a liveness check marks dead sessions **gone** (NFR-R5) |

Agent status is the one case where derivation genuinely fails: a running agent
process looks identical whether it is thinking or waiting for you. That state is
semantic and must be pushed out by the agent's own lifecycle events.

**Hooks are installed in the user's global agent settings**, guarded so they do
nothing when the workspace environment variables are absent. This is more
reliable than injecting settings at launch — it also captures an agent the user
starts by hand inside a workspace — and it means atelier does not need to own
the launch command.

### 5.3 Data

One versioned JSON file under the user's state directory. Single writer at a
time, atomic replace (NFR-R4).

```
Workspace
  slug          string     immutable; the directory name
  title         string     generated, mutable, display only
  intent        string     the text the user typed
  created       timestamp
  session       string     tmux session name
  prs           []PR       cache; refreshed on agent stop
  prs_refreshed timestamp
```

```
PR
  repo, number, title, url
  state           open | draft | merged | closed
  ci              pass | fail | pending | none
  review          approved | changes_requested | review_required | none
  registered      bool      true if registered rather than discovered
```

**Worktrees are not stored.** They are derived from the filesystem on every
read (NFR-R2). Agent status is not stored durably — it is per-session runtime
state, reset on start.

### 5.4 Interfaces

| Interface | Purpose | Consumers |
|---|---|---|
| **UI** | Everything the user sees and does | The user |
| **CLI** | Status writes and status-line reads | Agent lifecycle hooks; the terminal multiplexer's status line |
| **MCP** | `register_pr` — the FR-G2 gap-filler | The agent |
| **tmux fragment** | Bindings the user sources into their own config | The user, once, at install |

The CLI is deliberately small: it exists so hooks and the status line have
something fast to call. It is not a user-facing surface.

### 5.5 Process and control flow

**Creating a workspace (FR-A1):**
1. User types intent, presses Enter.
2. Directory created under a slug derived from the intent plus a short unique
   suffix. Immutable from this moment.
3. tmux session and agent window created, cwd set to the workspace root,
   identifying environment variables set on the window.
4. Agent starts with the intent as its opening prompt.
5. **Asynchronously:** title generated and written to state; the UI updates when
   it lands. Creation never waits on this (NFR-P2).

**Agent reports status (FR-B1, FR-B3):**
Agent lifecycle event fires → hook invokes the CLI with the workspace and window
identity from its environment → status written → status line reflects it within
one second.

**Refreshing pull requests (FR-E4):**
Agent stop event → hook triggers a refresh for that workspace → worktrees derived
from the directory → branches read from each → one batched query per repository →
results merged with any registered PRs → written to the cache. The UI renders the
cache immediately and updates when the refresh lands.

## 6. Rules

Tripwires, not sentiments. Every one of these exists because its absence has a
predictable failure mode.

- **One agent. One forge. One renderer.** A second implementation requires
  deleting the first.
- **No plugin system, ever.**
- **State lives in one file, never in the terminal multiplexer.**
- **No process spawn per view.** If it draws, it draws inside the one warm
  process.
- **Extract an interface only when a second real implementation exists and is in
  production.** Never for a mock, never for a hypothetical.
- **Nothing polls.** If something needs to know when a thing changed, an event
  tells it.
- **A feature ships only after it has been wanted three separate times.**
- **5,000 lines of `internal/`.** Adding past it means removing first.

---

## 7. Out of scope for v1

Deferred deliberately. Each requires the three-times rule to return.

- Creating, merging, checking out, commenting on, or reviewing pull requests
- CI log inspection or failure triage
- Workspace rename, tagging, grouping, or archiving
- Any summary or recap of what an agent did
- Repository indexing, caching, or search
- Multi-agent or multi-forge support
- Any diagnostic, doctor, or self-check subsystem
- Session history or recovery of deleted workspaces

---

## 8. Open for discussion

Deliberately unresolved. These want a decision before or during implementation,
not a guess now.

1. **Title generation model.** A short structured naming call is latency-
   sensitive but not quality-sensitive. Which model, and is the cost worth the
   ergonomics versus a deterministic slug?
2. **Scratch shell cleanup.** FR-D3's persistent shells outlive their workspaces
   unless reaped. Prune on UI start, or on workspace delete, or both?
3. **First-run experience.** What happens on a completely fresh install with no
   config and no workspaces?
4. **Uncommitted-change policy on delete (FR-F1).** Warn and allow, or refuse
   until resolved?
